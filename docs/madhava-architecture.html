The architecture, layer by layer

Agents talk to each other over A2A. Agents use tools over MCP. Rules and plan data meet only inside the deterministic evaluator, so a model never decides whether a rule applies. It only selects candidates and explains results.

What happens when someone asks “why?”

The same eight steps run for every question. Only the set of domain agents changes.

  1. Anchor on the claim

    The orchestrator calls claim tools once and stores a snapshot. It extracts outcome tokens: each reject code, each pricing component, each DUR flag. These are the facts the final answer must explain.

  2. Resolve the date context

    Date of service picks the plan version and the rule set in force. The user can ask for rules as of today instead, to answer “would this happen now?”

  3. Route to domains

    A deterministic table maps reject codes and outcome fields to domains. For free-text questions, a small model adds domains. Cheap neighbouring domains are included speculatively, so nothing waits on a second round.

  4. Fan out over A2A

    Each selected agent receives a task with a context reference, not a copy of PHI. All tasks start together under one deadline, typically four seconds.

  5. Find candidate rules

    Each agent queries the rule registry inside its own domain by trigger, then by vector similarity when the question is fuzzy. Only rules effective on the claim's date come back.

  6. Fetch only the plan paths each rule reads

    The rule card lists its plan paths. The plan slice service returns just those values for the plan version, usually from cache.

  7. Evaluate and return findings

    The evaluator runs the rule condition and returns fired or not fired, with the exact claim and plan values used. The agent returns structured findings, streaming each as it completes.

  8. Synthesize and check coverage

    The synthesizer orders findings by adjudication precedence and confirms every outcome token is explained by at least one finding. Anything unexplained is stated as a gap and logged for SMEs, never filled in by the model.

How rules link to API data

The rule card is the join. Its triggers make it findable from a claim outcome. Its reads tell the plan slice service which of the 12k fields to fetch. The field catalog gives every path a meaning, owner and type, so CI can reject a rule that points at a path the API no longer has.

Why the answers can be trusted

The adjudication engine emits no rule trace, so every explanation is a reconstruction. These controls make that explicit and measurable.

Deterministic decisions

Whether a rule fired is decided by the CEL evaluator on real values. The model selects candidate rules and turns findings into language.

Confidence levels

Confirmed when the rule's declared outcome matches the actual response exactly. Consistent when it fits but another rule could too. Unverified when inputs were missing.

Outcome coverage check

Every reject code and pricing component must be explained by at least one finding. Uncovered outcomes are shown as gaps and become the SME backlog.

Precedence resolution

When several rules fire, the synthesizer orders them by adjudication sequence: eligibility, coverage, UM, DUR, network, pricing. The first blocking rule is the primary reason.

Rules as they were

Rule cards carry effective dates and versions. Old claims are explained with rules in force on the date of service. A rules-as-of switch shows how today's rules would treat the same claim.

Replay against reality

Golden claims with known outcomes run in CI on every rule change. The headline metric is match rate: the top finding agrees with the engine's actual result.

Scaling to enterprise volume

Parallel fan-out makes latency roughly the slowest agent instead of the sum of all agents. The rest of the speed comes from keeping models out of the hot path where they are not needed.

Run one by one, the same eight agents take 15 to 20 seconds. Inside each agent, plan slices from cache take about 20 ms and rule evaluation under 10 ms. The model call is the dominant cost.

Cache what rarely changes

Plan slices are cached by plan ID, plan version and path set. Plan versions change rarely, so hit rates are high. Rule cards live in agent memory and are refreshed by MongoDB change streams.

Cache whole explanations

The key is claim ID, rules-as-of and rule set hash. A claim asked about by three people in an hour is explained once. Any rule change in that domain invalidates it.

Scale each agent on its own

Each agent is its own GKE deployment, autoscaled on in-flight tasks through KEDA or custom metrics. Pricing and UM agents get the most traffic and scale independently of the rest.

Deadlines and partial answers

Every A2A task carries a deadline. A slow agent's result is marked pending and the answer goes out with what is confirmed. Bulkheads stop one domain's failures from consuming shared capacity.

Protect the plan setup API

All access goes through the plan slice service with circuit breakers, request coalescing for identical slices, and per-path projection so callers never pull the full 12k-field payload.

Right-size the models

Domain agents use a small, fast model, or skip the model when the route table and templates are enough. The synthesizer uses a stronger model. The LLM gateway handles quotas, prompt caching and fallback.

Batch mode for audits

Thousands of claims for audits or client reviews go through a queue such as Pub/Sub. Batch workers use the same agents with lower priority and no streaming.

Discovery, not wiring

The orchestrator reads agent cards from a registry. A new domain team ships an agent with its card and rules, and routing picks it up without an orchestrator release.

Security, privacy and audit

Minimum necessary data

Agents receive a context reference and fetch only the claim and plan paths their rules read. PHI never goes into the vector index, which holds rule text only.

Scoped identities

Every agent has its own workload identity and OAuth2 scopes. The UM agent can call UM rules and UM plan paths, nothing else. Agent-to-agent traffic uses mTLS.

Reproducible explanations

Each answer is stored with the claim snapshot reference, plan version, rule IDs and versions, evaluated inputs and final text. Auditors can replay it exactly.

Prompt injection hygiene

Free-text claim fields and rule prose are passed as data, never as instructions. Tool scopes limit what a manipulated agent could reach anyway.

Approved model endpoints

Models run only through the LLM gateway on endpoints approved for PHI, with retention controls and redaction in logs and traces.

Rule governance

Rules move from Git pull request to SME review, schema and path validation, golden-claim replay, then publish. A UI editor later writes to the same pipeline.

Observability and quality

One trace ID follows the question through the orchestrator, every A2A task and every MCP tool call. That makes a slow or wrong answer diagnosable in minutes.

Getting there in three phases

Prove explanations

  • One agent, two domains: UM and coverage
  • Rule cards in Git, published to MongoDB
  • Plan slice service, CEL evaluator, field catalog
  • Golden claim replay and match rate

Split into domain agents

  • Orchestrator with A2A fan-out and deadlines
  • Agent cards and registry-based routing
  • Pricing what-if, DUR and eligibility agents
  • Explanation cache and per-agent autoscaling

Run at enterprise scale

  • All domains, plan change history agent
  • Batch mode for audits and client reviews
  • UI rule authoring on the same pipeline
  • Rules-as-of comparisons for any claim

    Why Python for agents and Java for tools
    
    
    The split follows how often each part changes and what it depends on. Agent logic is prompts, routing and evaluation, and it changes weekly. Tool servers are integrations with systems of record, and they change rarely.
    
    
    
      
    Agent tooling lands in Python first
    ADK, LangGraph, evaluation frameworks and tracing tools ship features in Python before anything else. Agent behaviour is where iteration speed pays off.
    
      
    ADK fits the platform
    Built-in A2A for calling and exposing agents, workflow agents for fixed graphs, LiteLLM for any approved model, and a straightforward path to GKE.
    
      
    Tools stay with the Java estate
    The plan slice, rule registry and evaluator wrap existing Java APIs, reuse the team's security and logging starters, and are throughput-bound rather than agent-shaped.
    
      
    MCP is the language boundary
    Agents only see typed tool schemas. Either side can be rewritten without the other noticing, and IDE assistants and SME tools reuse the same tools.
    
      
    The cost is two runtimes
    Two build pipelines, two base images and Python skills on the team. Shared service templates for each language keep the difference small.
    
      
    When to choose LangGraph instead
    If you want the flow as an explicit state graph with built-in checkpointing and replay of each run, LangGraph is the better fit. A2A still connects it to the same domain agents.

    A fixed graph, not an open loop
    The orchestrator runs the same steps in the same order every time. A model never decides which tool to call next, so it cannot skip the coverage check or invent a path.
    
      
    Bounded cost and latency
    Two orchestrator calls and at most one small call per agent, all known in advance. Prompt caching on the shared instructions cuts the cost further.

    Orchestrator as an ADK graph, Python
    
        
    A fixed sequence. Only two steps are model calls; the rest are plain code.
    

    understand = LlmAgent(
    name="understand", model=SMALL_MODEL,
    instruction=UNDERSTAND_PROMPT,
    output_schema=Ask, output_key="ask")

synthesize = LlmAgent(
    name="synthesize", model=STRONG_MODEL,
    instruction=SYNTHESIZE_PROMPT,
    output_key="answer")

orchestrator = SequentialAgent(
    name="claim_explainer",
    sub_agents=[
        Snapshot(),       # MCP get_claim, no model
        understand,       # model call 1, small
        Route(),          # route table, no model
        FanOut(),         # A2A in parallel, no model
        CoverageCheck(),  # precedence, gaps, one gap round
        synthesize,       # model call 2, strong

    Dynamic fan-out with deadlines, Python
    
        
    Only the routed domains run. A late agent becomes a pending finding instead of a failure.
    

    class FanOut(BaseAgent):
    async def _run_async_impl(self, ctx):
        state = ctx.session.state
        ref, domains = state["context_ref"], state["domains"]

        async def ask(domain):
            try:
                return await asyncio.wait_for(
                    agents[domain].explain(ref),  # A2A
                    timeout=4.0)
            except Exception as ex:
                return Finding.pending(domain, str(ex))

        findings = []
        for done in asyncio.as_completed(
                [ask(d) for d in domains]):
            f = await done
            findings.append(f)
            yield progress_event(self.name, f)  # SSE
        yield Event(author=self.name,
            actions=EventActions(state_delta={
                "findings": [f.model_dump()
                             for f in findings]}))

    AI, agents, harness, loops and graphs in Madhava
    
  
    Yes, Madhava follows this layered pattern. Each layer answers a different question, and the design puts most of the correctness in the harness and the graph, so the model is the smallest part of the system.
    

    


    
  
    
    
    
      
    The twist: the request path is a graph of bounded steps, not an open agent loop. Runtime loops are short and capped, with a deterministic check deciding when to stop. The loop that makes Madhava better over time runs outside the request: golden-claim replay finds gaps, SMEs write rules, and CI proves them before they go live.
    
    
    

    
    Each layer wraps the one inside it
    
    
    Select a layer to see its role, the Madhava parts that implement it, and the steps to build it.
    
    
    
      
    
        
    
          
          
    
            
            
    
              
              
    
                
                
    
                  
                
    
              
    
            
    
          
    
        
    
      
    
      
    
    
    
  
    

    


    
  
    
    
    The request graph, with its one runtime loop
    
    
    Every question runs through the same nodes in the same order. Two nodes call a model. The only back edge is the gap round, and the coverage check allows it at most once.
    
    
    
      
    
    
    
    
      Deterministic node
      Model call

    Every loop has a verifier and a cap
    
    
    A loop is only safe when something other than the model decides it has succeeded. These are the four loops in Madhava.
    
    
    
      
    
        
    LoopRunsWhat repeatsVerifierStops when
    
        
          
    Gap roundPer question, orchestratorA small model proposes more domains, which are fanned out againCoverage check on outcome tokensAll tokens explained, one extra round used, or the deadline reached
    
          
    Retrieval fallbackPer question, inside a domain agentNo candidate rule fired, so the agent widens to vector search and evaluates againCEL evaluatorA rule fires, or one widened attempt is done
    
          
    ConversationPer sessionFollow-up questions reuse findings already gatheredCoverage check per answerThe user stops, or the session limit is reached
    
          
    ImprovementWeekly, offlineGolden replay, gaps and feedback become rule changes that are tested and publishedMatch rate and gap rate on golden claimsEach change must hold or raise the match rate before it merges
    
            
      
    
    
    
  
    

    


    
  
    
    
    Build order: inside out by risk, not by layer name
    
    
    Correctness lives in the harness, so build and prove it before any model is involved. Loops come last because they only help once there is a reliable verifier to stop them.
    
    
      
      
    1. Harness, proven without a model
      Field catalog, plan slice service, rule cards, CEL evaluator and rule registry. Exit when a plain script explains a golden claim end to end using only the tools.
      2. 
      
    2. One agent and its models
      The utilization management agent from the shared template, with the small model phrasing findings. Exit when it returns valid findings for its golden claims inside the deadline.
      3. 
      
    3. The graph
      Orchestrator graph with understand, route, fan-out, coverage check and synthesize, over two or three domains. Exit when answers cite only findings and every run can be replayed.
      4. 
      
    4. The loops
      Gap round and retrieval fallback with hard caps, then the weekly improvement loop feeding the SME backlog. Exit when each loop has a dashboard showing its trigger rate and outcome.
      5. 
      
    5. Scale the graph
      Add the remaining domains as new nodes through agent cards, then the batch and rules-as-of graphs. Exit when a new domain ships without an orchestrator release.
